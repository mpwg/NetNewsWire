# Native Reader application

Open `Reader.xcodeproj` in this directory and select the shared Reader scheme. This project was created through Xcode MCP with Apple's multiplatform SwiftUI app template. It links the six existing ReaderKit libraries; the standalone store recovery probe is not an app dependency.

ReaderTests is an unhosted Swift Testing code-test target. All code-testable behavior, including connection validation and CI runner failure propagation, belongs here. CI bootstraps the Swift runner contracts directly before trusting the aggregate shell script. ReaderUITests is a small native XCTest/XCUIAutomation target. Apple's automatic scheme test plan discovers both; no generated project, scheme or test-plan script is required. Use Xcode MCP for interactive builds, tests and project changes.

Prefer the smallest Swift Testing boundary that proves the behavior. Pure unit tests cover business rules; isolated service/store integrations cover I/O contracts. Actual WebPage documents and NSHostingView component lifetimes also run with Swift Testing. Use XCUIAutomation only when native app input, focus, scene bindings or visible controls are necessary. Do not duplicate state/cancellation/error matrices through UI automation. The existing seven native UI methods remain unchanged; the expanded HTML5, content-isolation and actual HTTP-request matrix runs entirely in Swift Testing. See [current content-isolation evidence](../docs/reader/evidence/f-active-content-2026-10-25.md) for exact counts and scoped acceptance.

Current development verification focuses on My Mac. Push and pull-request CI run macOS; the Reader OS 27 workflow's manual `coverage: all` option retains the complete Mac/iPhone/iPad matrix for final acceptance. iOS and iPadOS revalidation is deferred until then, rather than inferred from Mac results. The aggregate runner still supports every platform and propagates failures.

The shared Reader scheme launches Debug by default. Profiling and archiving use Release. Temporary Release checks must restore and save the Debug launch configuration through Xcode afterward.

Every native target enables Swift 6, complete concurrency checking, Approachable Concurrency and Swift/C-family warnings as errors. ReaderKit applies the equivalent package settings to every target. Debug and Release use separate bundle IDs and storage namespaces. See the [Reader guide](../ReaderKit/README.md) for account setup, architecture and acceptance limits.

The UI smoke launch uses `--ui-testing` with an isolated in-memory store. It requires no personal account. The first Mac window must appear automatically, without Command-N. Selection, search, sheets and query generations belong to each scene; repository and account services are shared.

The Mac-only image-load UI scenario adds `--ui-testing-image-load` in Debug. Both arguments are required. It seeds 50 in-memory feeds and injects a local URLProtocol transport into the shipping IconService/FeedImageService pipeline; no account client or credential store is created. Explicit start keeps the workload from finishing before the test is ready. Approximately 190 KiB homepages advertise icons that return HTTP 503 before a 4096×4096 PNG fallback. The first fallback delivers; later replies wait in cancellation-aware streams until their actual row tasks end. The native test observes held requests, scrolls and edits/cancels the real account form, then removes fixture feeds through ReaderStore and requires new cancellations with both active and held counts at zero. This replaces a four-second timing assumption that failed on CI after all replies finished normally. Deadlines and cancellation assertions remain. [Failure and controlled-fixture evidence](../docs/reader/evidence/f-active-content-image-gate-2026-10-25.md). Counter and window-only screenshot attachments preserve the result. Service/order/error matrices remain Swift Testing contracts; this native case proves actual row-task wiring and input responsiveness, not energy or device acceptance.

The Mac window scenario reuses `--ui-testing-timeline` and verifies separate searches and rendered selections, closing one window during another’s held query, and real corner resizing from 1200×800 to 960×640 and back. Query, selection and sheet-state rules remain in Swift Testing; this UI case proves the actual scene bindings and native events. Debug diagnostics occupy a separate area below the Reader so they cannot obscure its footer. See [E window evidence](../docs/reader/evidence/e-windows-2026-10-25.md).

Layout follows the available window and system safe areas. Article rendering uses WebView/WebPage with content JavaScript disabled. Physical-device, iPad multiwindow, VoiceOver, Dynamic Type, keyboard, RTL and sustained-load checks require separate evidence.

New Mac windows request up to 1200×800 points, capped to their SwiftUI placement context's visible display rectangle with room at the edges. This keeps sidebar and title-bar controls on smaller displays. The system retains normal user resizing, placement and state restoration; no global screen lookup or UI-test-only geometry override is used.

The Mac-only full-text UI fixture uses both `--ui-testing` and `--ui-testing-content` in Debug. Two synthetic saved articles use an injected URLProtocol transport: A holds its request until cancellation; B returns HTTP 403. One native scenario selects A, starts extraction through the real menu, selects B and requires A's transport cancellation. It then verifies B's actual alert, localized saved-content warning and readable WebKit heading. Its state/error variants, parsing, stale delivery and weak graph release belong to Swift Testing. No account client, Keychain or external server is involved. [F rendering evidence](../docs/reader/evidence/f-rendering-2026-10-25.md).

The full-text streaming contracts remain Swift Testing. Three functions / seven executions hold native transport completion to distinguish early header/size/cancellation handling from rejection after downloading everything. They cover absent and inaccurate length headers, an exactly 4,000,000-byte article, two explicit cancellation stages and weak service/session/plan release. No additional UI method is used for these I/O rules. [F streaming evidence](../docs/reader/evidence/f-streaming-2026-10-25.md).
